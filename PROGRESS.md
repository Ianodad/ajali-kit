Points it at `--font-geist-sans` (the Geist variable `layout.tsx` already loads) with a `ui-sans-serif, system-ui, sans-serif` fallback chain.
- P3.1 `scripts/smoke-muse.ts` and `scripts/smoke-sam.ts`: real-API smoke scripts per SPEC 10.1/10.3/10.4, written only, never run here (no key in this environment; Ian runs them with `npx tsx scripts/smoke-muse.ts <photo>` and `npx tsx scripts/smoke-sam.ts <photo> [concept]`). Both build their own `OpenAI` client inline from `MODEL_API_KEY`/`META_BASE_URL` env vars rather than importing `src/lib/meta.ts`, since that module is `import "server-only"` and only loads inside Next's bundler. They reuse the same prompt/schema constants (`src/lib/schemas/damage-analysis.ts`) and the same SAM record-pairing helper (`src/lib/sam-parse.ts`) as the real routes, so a smoke-test pass is evidence the routes' real path works too. Neither logs the image bytes, the data URL, or raw mask payloads, only model, latency, usage and the parsed summary (SPEC 11).
- P3.2 `/api/analyze-photo`: zod request/response schemas and the Muse Spark prompt/JSON schema/instructions live in `src/lib/schemas/damage-analysis.ts` (transcribed from SPEC 8.2). Post-processing (clamp/sort box corners, drop boxes under 1% of the grid, convert to pixels, cap at 16 items) is one shared function, `src/lib/analyze-photo-mapping.ts`, used by both the mock and real branches, so a mock response always gets mapped through the exact same pipeline as a real one. Mock fixtures (`fixtures/analyze-photo.ts`) cover the demo scenario (two items, a rear-end collision) plus the "no damage" and "not a vehicle" F4 edge states; because `box_2d` stays in the 0..1000 grid, the fixture lands on a plausible spot on the vehicle regardless of the real photo's aspect ratio. Real-path retries (`src/lib/ai/retry.ts`) cover 429/5xx (exponential backoff with jitter, starting 500ms, honouring `Retry-After`) and, separately, a JSON-parse or zod-validation failure on the model's own output (SPEC 8.1's "retries ... on parse failure"). Logs model, latency and `usage` only, never image data.
- P3.3 `/api/segment` (`mode: "concept"` and `mode: "boxes"`): the real path builds the prompt with `buildObjectPrompt` (box mode) or the bare concept string, calls the streaming Responses API, and parses it with the real `@meta-sam/parser` (`parseImageStream`, `recordsOfKind`, `decodeMaskToSVGPath`, `decodeMaskToRaster`) via a shared pairing function, `src/lib/sam-parse.ts`, that pairs box and mask records by `objectId`, decodes the mask and scales its 1-count to source-pixel area exactly as SPEC 8.3 describes. A zero-match result is treated as valid, not an error, per SPEC 8.3. The mock path (`src/lib/mock/segment-mock.ts` + `src/lib/mock/blob-path.ts`) synthesizes a deterministic, inset, wobbly polygon per requested box (not the box's own rectangle) plus a near-full-frame vehicle silhouette for concept mode, with its reported area computed from the actual polygon via the shoelace formula, so mock masks look plausible on any real photo and are geometry-consistent with whatever box was requested.
- Unit-tested the real parser path end to end (`src/lib/__tests__/sam-parse.test.ts`), not just the mock: `@meta-sam/parser` exports only `decodeMaskToRaster`, not the encoder that built it (its own source calls that encoder "internal ... used to create deterministic synthetic conformance data"), so `src/lib/__tests__/support/sam-mask-codec-mirror.ts` reimplements that one_bit range-coder encoder from the published source to build a real, valid, round-trippable mask payload for a hand-built wire-format record. The test feeds that through the actual `parseImageStream`, not a mock, and asserts the decoded box, raster size, area and SVG path are all correct; `/api/segment`'s own route test reuses the same encoder for one real-parser case (`src/app/api/segment/__tests__/route.test.ts`).
- P3.4 `src/lib/box-convert.ts`: `clampBoxNorm` (sort swapped corners, clamp to 0..1000), `isBoxNormTooSmall` (SPEC 8.2's 1%-of-grid drop rule) and `boxNormToPixels` (exact-size conversion, plus a minimum-pixel-size expansion for a rounded-degenerate box, clamped back inside the image at an edge). Unit tested for portrait and landscape photos (A5: "no offset or stretch").
- P3.5 client orchestration, `src/lib/damage-pipeline.ts`: `analyzeDamagePhoto` runs analyze-photo, then (if a vehicle with damage) the concept and box segment calls in parallel; `runDamagePipeline` runs that over several photos through `src/lib/concurrency.ts`'s `mapWithConcurrency`, capped at 3 in flight (SPEC 10.6), with one photo's failure isolated from the rest. Progress callbacks report `finding_damage` / `marking_area` / `done` / `error` per photo. The "largest vehicle mask that overlaps most of the damage boxes" pick (F4 step 4) lives here, not in the route, since the route's concept call has no knowledge of the damage boxes; it can return more than one vehicle candidate and the client picks by intersection-area overlap. A failed vehicle (concept) call degrades gracefully (no vehicle outline or percentage, matching the "SAM finds no car" edge state); a failed box-masks call is a real failure and rejects, since without it there is nothing to show.
